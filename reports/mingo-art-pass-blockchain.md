# MINGO ART PASS 블록체인 조합 검토 보고서

- 문서 버전: 1.1
- 상태: **기술선정 제안 / 구현 전 검토**
- 조사 기준: 2026-11-10
- 문서 정리: 2026-11-14
- 대상: MINGO ART PASS 인증서의 발급·정정·폐기 및 플랫폼 내 보유 확인 이력

> 이 보고서는 공개 공식 문서와 공개 소스를 바탕으로 한 기술 추천이다. 블록체인 연동 구현, 메인넷 배포, 보안 감사, 실제 가스비 측정이 완료됐다는 뜻이 아니다. 네트워크·제품의 배포 버전, 요금·제약은 도입 직전에 재확인한다.

## 1. 결론

**Base + NFT 없는 소규모 ART PASS 전용 등록부**를 권장한다. 기존 NestJS API·MongoDB·Cloudflare R2를 유지하고, 승인된 인증서의 지문과 현재 버전·상태만 외부 원장에 기록한다.

사용자는 기존 계정으로 신청하고 QR로 결과를 확인한다. 사용자에게 가상자산 지갑 설치·코인 구매·가스비 결제를 요구하지 않는 UX를 목표로 한다. 서비스 운영자는 별도의 발급 계정과 수수료를 관리한다.

Base가 모든 대안보다 가장 저렴하거나 유일한 정답이라는 뜻은 아니다. 현재 TypeScript/NestJS 환경과 제한된 업무 규칙에 맞춘 권고다. 인증 정책을 먼저 정하고, Base Sepolia 테스트넷에서 검증한 뒤 소량 메인넷 운영으로 진행한다.

## 2. 쉬운 설명과 신뢰의 한계

Base는 Ethereum 계열 도구를 사용할 수 있는 블록체인 네트워크다. MINGO의 원본 저장소를 대체하기보다, 승인 당시 기록과 나중에 제시하는 기록을 비교할 외부 기준점으로 사용한다.

해시는 인증서의 내용을 정해진 규칙으로 계산한 ‘디지털 지문’이다. 같은 규칙으로 다시 계산해 기록된 지문과 비교한다. 해시만으로 원문 전체를 복원할 수 있는 것은 아니지만, 단순 개인정보 해시는 추측·재식별될 수 있으므로 공개해서는 안 된다.

- **확인 가능한 것:** 지정 발급자가 어떤 기록을 게시했는지, 제출한 공개 인증서와 게시된 지문이 일치하는지, 현재 정정·폐기 상태가 무엇인지.
- **자동 보장하지 못하는 것:** 작품의 진품성, 실물 인도·대금 지급, 적정 가격, 법적 소유권.
- **별도 필요한 것:** 발급 주체 확인, 제출 자료 심사, 실물과 인증서 연결, 분쟁·오승인 대응.

> 권장 고지: “온체인 확인은 해당 인증 기록의 무결성과 현재 상태를 확인하는 절차입니다. 작품의 진품성, 가격 및 법적 소유권을 보증하지 않습니다.”

## 3. 비교한 대안과 선택 이유

### 3.1 Base + 전용 비토큰형 등록부 — 권장

전용 등록부는 발급·정정·폐기·최신 상태 확인만 담당하는 작은 스마트 컨트랙트다. NFT 소유자나 토큰 이전 기능은 넣지 않는다.

- 작품별 현재 digest·revision·status를 명시적으로 관리한다.
- 같은 eventId의 중복 처리를 거부하거나 기존 결과로 복구하는 규칙을 정한다.
- expectedRevision을 검사해 동시 정정 중 한 요청만 유효하게 처리한다.
- 관리 권한과 자동 발급 권한을 분리한다.
- 기존 키를 분실했을 때 권한 교체 후 허용된 정정·폐기를 수행하는 정책을 설계한다.

이 규칙은 Base가 자동 제공하는 기능이 아니라 직접 구현하고 검증할 업무 로직이다. 컨트랙트가 작다고 안전성이 보장되지는 않는다. 독립 검토와 테스트가 필요하다. 초기에는 업그레이드 프록시를 기본 도입하지 않고, 새 계약 버전으로 이전하는 명시적 절차를 준비하는 안을 권한다.

### 3.2 EAS — 범용 증명 생태계 연동이 중요할 때

Ethereum Attestation Service(EAS)는 범용 증명 기록 기반으로 유용하다. 다만 검토한 공식 계약에서는 다음 업무 규칙을 기본 제공하지 않는다.

- refUID는 참조 기록의 존재를 검사하지만, 같은 작품의 최신 버전·동일 발급자·단일 이력 순서를 자동 보장하지 않는다.
- 새 발급 요청의 UID가 유일하다는 것과 업무 eventId가 한 번만 처리된다는 것은 다르다. 같은 내용을 다시 보내 별도 증명을 만들 수 있다.
- 원래 발급자만 해당 증명을 취소할 수 있는 선행 검사가 있다. 새 운영 키가 이전 키의 증명을 자동으로 취소할 수 있는 것은 아니며, resolver만으로 이 검사를 우회할 수 없다.
- isAttestationValid라는 이름만 보고 취소·만료·최신성까지 검사된다고 가정해서는 안 된다. 검토 소스의 해당 함수는 존재 여부를 검사한다.

엄격한 ART PASS 규칙을 체인에서 강제하려면 stateful resolver와 안정된 발급자 주소/별도 무효화 정책 등 추가 설계가 필요하다. 따라서 ‘기존 EAS를 붙이면 별도 계약이 전혀 필요 없다’고 결론내리지 않는다.

여러 기관의 서로 다른 증명을 표준 생태계로 연결하는 요구가 커지면 재검토할 수 있다. EAS가 본질적으로 불안전하다는 의미는 아니다.

**검증 범위:** EAS upstream commit e6e970286ff18bbdfc5d8eff2742c5ece46040e4의 계약 소스와 OP upstream의 관련 소스를 조사했다. Base 현재 배포 구현·version()·서명 domain의 실체인 대조는 읽기 요청 차단으로 완료하지 못했다. 소스 분석 결과를 실제 운영 연동 성공으로 표현하지 않는다.

### 3.3 Bitcoin + OpenTimestamps — 과거 존재 증명이 주목적일 때

OpenTimestamps는 어떤 데이터가 특정 시점 이전에 존재했음을 증명하고 독립 검증하는 방식이다. 공식 사이트는 등록/API 키 없이 이용하는 무료 공개 calendar 서버를 안내한다. 무료 제공이 SLA나 영구 가용성 보장은 아니다.

단순 타임스탬프만 필요하다면 유력한 대안이다. 다만 ‘현재 어떤 인증서가 최신인지’, ‘폐기됐는지’ 같은 동적 업무 상태는 별도 체계로 관리해야 한다. 제안된 ART PASS 전체 상태 모델을 이것만으로 대체하지는 못한다.

### 3.4 NFT·사설 체인·VC

- **NFT:** 현재 목표가 토큰 거래가 아니므로 초기 도입에서 제외한다.
- **사설 블록체인:** 여러 기관이 운영·합의 책임을 나눌 실제 협력 구조 없이 시작할 필요는 없다는 판단이다.
- **W3C Verifiable Credentials:** 향후 기관 간 증명 교환 형식의 후보다. 그 자체가 블록체인이나 진품 보증 시스템은 아니며, 임의 JSON을 만든 것만으로 VC 표준 준수라고 표시하지 않는다.

## 4. 추천 기술 조합

### 기존 서비스와 저장소

- 고객 웹·관리자 웹: 기존 Next.js 환경에 신청·검토·검증 화면을 연결한다.
- API: 기존 NestJS에서 사용자/검토자 권한과 업무 상태를 관리한다.
- DB: 기존 MongoDB에 현재 상태·변경 이벤트·Outbox를 저장한다.
- 파일: 기존 private R2에 원본 증빙·스냅샷·증명 패키지를 보관한다.

### 블록체인과 연결 도구

- 네트워크: 개발 Base Sepolia, 검증된 소량 운영은 Base Mainnet.
- 컨트랙트: Solidity로 작성한 소규모 비토큰형 등록부.
- 권한 관리: OpenZeppelin AccessControl 계열. 관리자 이전 지연·2단계 수락은 AccessControlDefaultAdminRules 등을 검토한다.
- 서버 연결: TypeScript 라이브러리 viem.
- 테스트: 기존 TypeScript 환경에 맞춰 Hardhat 등을 사용하고 계약/서버 통합 테스트를 분리한다.

라이브러리를 재사용하더라도 완성된 MINGO 계약 전체가 감사된 것은 아니다. 패키지·컴파일러·네트워크 버전은 구현 시 고정하고 검토한다.

### 작업 처리와 서명

- MongoDB Outbox를 먼저 저장하고 별도 Node.js 워커가 체인 전송·확인을 수행한다.
- MongoDB replica set/Atlas 트랜잭션 사용 조건을 확인한다. DB와 Base를 한 원자적 트랜잭션으로 묶을 수는 없다.
- 워커 임대·재시도·처리 순서·전송 nonce·미확인 전송·대체 트랜잭션을 관리한다.
- 주기적 Reconciler로 DB와 온체인 상태를 대조한다.
- 관리자 권한은 Safe 같은 복수 승인 방식, 자동 발급 키는 별도 보안 서명 서비스를 검토한다.
- AWS KMS의 secp256k1 지원은 후보 근거일 뿐, Ethereum 서명 어댑터·권한·리전·키 복구 검증이 완료됐다는 뜻은 아니다.

초기에는 Redis·Kafka를 추가하지 않는 구성을 권한다. 이는 예상 범위에 대한 설계 판단이며 실제 처리량 테스트 결과가 아니다.

Vercel의 상시 워커 기능 또는 별도 관리형 컨테이너가 실행 환경 후보다. 조사 당시 Vercel Daemons는 beta였다. 베타 제약·환경 격리·비용을 도입 직전에 확인한다. 일반 API 요청 안에서 체인 최종 확정을 계속 기다리는 구조는 피한다.

## 5. 데이터 공개 정책과 독립 검증

### 온체인에 기록할 범위

- 무작위 작품 식별자
- 업무 eventId
- 공개 인증서의 digest
- revision과 action/현재 상태

### 공개하지 않을 범위

- 실명·전화번호·이메일·주소·계정 식별자
- 거래 당사자 정보와 비공개 증빙 내용
- 접근 토큰·Presigned URL·비밀키
- 재식별 위험을 검토하지 않은 개인정보 해시

공개 인증서는 허용 필드만 추출하고 RFC 8785 JCS 정규화·UTF-8·Keccak-256 규칙으로 재현 가능하게 만든다. schemaVersion·nonce·previousDigest 등을 고정된 스키마에 포함한다. 파일의 SHA-256은 서버가 실제 저장 바이트를 검증하며 R2 ETag를 보편적인 SHA-256 대용으로 쓰지 않는다.

다운로드용 패키지에는 전체 공개 스냅샷, 해시 규격, chainId, 신뢰할 registry 주소와 revision 등을 담는다. 검증기는 신뢰할 체인·계약·발급자 정책을 함께 확인해야 한다.

**과거 파일의 해시가 맞는다는 것과 현재도 폐기되지 않았다는 것은 다르다.** 현재 유효성은 최신 체인 상태 조회가 필요하며, 오프라인 과거 증명만으로 최신 비폐기를 보장하지 않는다.

증빙 접근은 기존 권한 통제를 유지한다. Presigned URL은 발급 시 권한 확인과 짧은 만료시간을 사용하더라도, 유효기간 동안 링크 보유자가 접근할 수 있다. 다운로드마다 최신 철회를 반영해야 하는 자료는 API 전달 방식을 검토한다.

## 6. 실물 연결: QR부터, 보안 NFC는 다음 단계

초기에는 장기 유지할 서비스 도메인의 QR로 ART PASS를 조회하게 한다. 단순 QR이나 NFC UID가 존재한다는 사실만으로 실물의 진위를 보증하지 않는다.

보안 NFC가 필요해지면 NXP NTAG 424 DNA/TagTamper 등 암호 기반 태그와 훼손 흔적 라벨을 후보로 검토할 수 있다. 이는 태그 인증·변조 흔적 확인을 돕는 것이지, 작품 자체의 진품성이나 모든 태그 이식 공격을 해결하는 것은 아니다. 부착·키 주입·실물 사진·재검증·배송은 별도 운영 과제다.

## 7. 단계별 적용 순서

1. **업무 정책 확정:** 자기 등록/검토 완료 배지, 검토 주체, 공개 범위, 정정·폐기·재발급·분쟁 정책을 정한다.
2. **오프체인 업무 완성:** 신청·심사·이벤트 이력·QR 조회가 블록체인 장애와 독립적으로 동작하게 한다.
3. **Sepolia 검증:** 발급·중복·동시 정정·폐기·키 교체·전송 직후 종료·RPC 장애·재구성 시나리오를 시험한다.
4. **외부 검토와 운영 준비:** 계약 검토, 발급 키·관리 키 분리, 수수료 잔액·실패 알림, 백업·복구 및 사고 대응을 준비한다.
5. **소량 Mainnet 운영:** 검토 승인된 실제 대상만 발급하고 비용·지연·장애를 관찰한다. DEMO/자가 등록 기록을 실제 검증 완료 인증으로 승격하지 않는다.

체인 포함·확정·최종 확정 단계를 구분한다. 미확인 상태에 ‘블록체인 확인 완료’ 배지를 표시하지 않는다. 체인 장애가 기존 작품 등록·채팅을 중단시키지 않도록 상태를 분리한다.

## 8. 필수 검증과 운영 준비

- 정상 발급 후 공개 패키지와 온체인 digest 일치
- 공개 스냅샷 변조 시 불일치 감지
- 같은 eventId 재시도 시 중복 발급 방지 및 기존 결과 복구
- 동시 정정 시 revision 충돌 방지
- 전송 성공 직후 서버 종료 시 로그·영수증으로 복구
- 폐기 이후 과거 패키지를 현재 유효하다고 오인하지 않음
- 발급 키 분실·유출 시 권한 교체와 정정/폐기 경로 확인
- 비공개 증빙·개인정보·URL 토큰의 공개 응답/로그 비노출
- 실제 저장 바이트 검증과 파일 소실/기록 불일치 구분
- RPC 장애·체인 재구성·지연에 대한 재시도와 최종성 정책
- 장기 미처리 Outbox·반복 실패·가스비 잔액 부족·불일치 경보
- 독립 검토·운영 권한·백업 복구·재발급/마이그레이션 절차 확인

## 9. 비용과 아직 확인하지 않은 것

Base 비용에는 실행 비용과 L1 데이터 비용 등 여러 항목이 포함되며 네트워크 상황에 따라 달라진다. 월 비용을 특정 원화로 확정하지 않는다. 실제 계약 호출을 측정한 후 이벤트 수·RPC·워커·키 관리·모니터링 비용을 합산한다.

다음 항목은 본 조사에서 완료하지 않았다.

- 실제 ART PASS 컨트랙트의 배포·보안 감사
- Base 실배포 EAS 버전·서명 domain의 실체인 대조
- MINGO의 실제 발급량 기반 가스비·성능·처리량 측정
- 공급자 계약·견적·운영 SLA 확인
- 법적 소유권·감정 표현·개인정보 보존 정책의 법무 검토
- NFC 키트 구매·제작·부착·배송 또는 기관 제휴 체결
